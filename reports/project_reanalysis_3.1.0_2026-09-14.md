**MeDIAuto Studio 3.1.0 전체 재분석 — 2026-09-14**

기준: Git `4c98bf6`, `version.json` 3.1.0. 이전 2.0.2 분석과 개선 보고서를 현재 코드·테스트와 대조했다. 기존 미추적 `docs/platform-differentiation/` 문서는 그대로 유지했다.

**전체 판단**

대용량 WSI 조회, AI 분석, 조직·세포 주석, 검수와 임상정보 연결이 구현된 단일 기관용 웹 플랫폼이다. 뷰어와 백그라운드 작업의 자원 경합을 줄이는 설계가 강점이며, 3.0.0의 인증·조직 주석·감사 서명 개선은 회귀 테스트로 재확인했다.

현재 가장 시급한 문제는 청크 업로드의 경로 검증 누락이다. 허용된 업로드 계정이 업로드 디렉터리 밖에 청크를 기록하거나 오류 정리 과정에서 다른 디렉터리를 삭제하는 것을 임시 환경에서 재현했다. 다음으로 물리 면적의 보정값 출처, 세포 주석 동시 편집, AI 결과 캐시와 재다운로드를 보완해야 한다.

제품 이름에 SaaS가 있지만, 현재 구현은 단일 기관·단일 애플리케이션 프로세스 운영에 맞춰져 있다. 기관별 데이터 격리나 분산 작업 처리를 갖춘 다기관 SaaS로 평가할 근거는 확인하지 못했다.

**분석과 검증 범위**

- 백엔드 라우터, 인증, 파일 경로, 저장소, 타일/슬라이드 처리, AI 작업·캐시, 프론트엔드 API·면적 계산, 배포 문서를 확인했다.
- 백엔드 기존 테스트 **94개 통과**. 운영 연결 문자열을 쓰지 않는 임시 PostgreSQL 통합 테스트 포함.
- 프론트엔드 Node 테스트 **12개 통과**. 면적 계산·면적 도구·라벨 위치·조직 주석 revision 처리 포함.
- Python 107개 파일 AST 구문 검사, 프론트엔드 JS 23개 파일 구문 검사 통과.
- pydicom `get_frame_offsets` 사용 중단 예정 경고 1개. 테스트 실패는 아니다.
- 업로드 문제와 AI 결과 재요청은 임시 FastAPI 앱으로, 세포 저장은 모의 저장소로, 보정값 누락은 합성 슬라이드 객체로 검증했다. 운영 원본·DB·서비스에는 변경을 가하지 않았다.
- 실제 서비스가 이 커밋을 로드했는지, 실브라우저 전체 동작, GPU 추론 정확도·속도, 실제 동시 사용자 부하, 백업 복원은 검증하지 않았다. 이 보고서는 모든 코드 행에 대한 보안 감사나 임상적 성능 평가가 아니다.

**업로드 경로 문제 상세**

`upload/start`가 정상 발급한 ID는 12자리 16진수지만, `upload/chunk`와 `upload/complete`는 전달된 ID 형식·소유자·발급 이력을 검증하지 않는다. `UPLOAD_DIR / f"_chunks_{upload_id}"`를 그대로 사용하며, 다른 파일 경로에 쓰는 `safe_subpath()`와 같은 경계 검사도 없다.

임시 디렉터리에서 정상 업로드 세션을 만든 뒤 상위 경로 성분을 포함한 ID로 요청했을 때, 업로드 폴더의 형제 디렉터리에 `chunk_000000`이 기록되며 200을 반환했다. 같은 경로를 지정한 완료 요청에서 허용되지 않는 확장자를 주자 400 응답과 함께 형제 디렉터리 자체가 삭제됐다. 정리 코드가 검증되지 않은 `chunk_dir`에 `shutil.rmtree()`를 호출하기 때문이다.

익명이나 viewer 요청은 역할 검사에 막힌다. 그러나 업로드가 허용된 labeler·doctor·admin 계정에서 재현 가능한 문제다. 범위는 서버 프로세스가 접근·쓰기·삭제할 수 있는 파일시스템 권한에 제한되며, 이번에 운영 데이터 손실이 발생했다는 뜻은 아니다.

수정 완료 기준: ID를 발급 형식으로 제한하고 서버 세션에서 조회, 세션 사용자 확인, `resolve()` 이후 지정된 청크 루트 내부인지 검증, 심볼릭 링크·경로 이탈 거절, 검증된 세션 디렉터리만 정리. 모든 실패 분기에도 같은 경계가 필요하다.

**면적 계산과 3.1.0 기능**

고정 사각형과 원형은 X/Y 픽셀 간격을 각각 사용하며, 원형 polygon 근사의 면적까지 보정한다. 1·2·4·8 mm² 계산 및 편집 후 면적 재계산 테스트는 통과했다. AI/Tissue의 기본 2 mm²와 Cell 도구 유지도 테스트로 확인했다.

문제는 계산식보다 입력의 신뢰도다. `SlideInfo`는 X/Y MPP가 둘 다 있지 않으면 두 값을 모두 0.25로 설정한다. `/info`는 그 값을 보정 출처 없이 프론트엔드로 보낸다. 따라서 프론트엔드의 ‘값이 없으면 Area unavailable’ 처리는 서버가 이미 채운 기본값을 구별하지 못한다.

원본 속성이 빈 합성 슬라이드에서 `mpp_x=mpp_y=0.25`, 가로 10,000px의 물리 폭 2.5mm가 생성됐다. 실제 간격이 0.5인데 0.25로 가정하면 같은 픽셀 도형의 표시 면적은 실제의 1/4이 된다. 이는 수학적 예시이며 실제 원본의 측정 오차를 실측한 것은 아니다.

수정 완료 기준: 보정 출처와 유효성 필드를 전달하고, 메타데이터 없음·한 축만 있음·0/음수/비유한 값을 분리 처리. 미확인 원본의 물리 도구는 제한하거나 추정값임을 명시해야 한다. 일반 JPEG의 고정 20x/0.5 MPP 정책도 출처와 함께 표시하는 것이 적절하다.

**동시 편집과 저장 신뢰성**

조직 주석 snapshot은 수정됐다. 반면 세포 저장은 `list_cells` 전체를 revision 없는 `$set`으로 갱신한다. 두 클라이언트의 오래된 화면을 모사해 같은 패치에 순서대로 저장하자 두 요청 모두 200이며 마지막 목록만 남았다. 모의 DB로 라우터 계약을 검증했으며 실DB 동시 스트레스 시험은 아니다.

셀 목록 저장과 완료/검수 상태 갱신도 별도 저장소 호출이다. 중간 실패나 다른 사용자의 상태 변경이 끼는 상황을 트랜잭션과 조건부 갱신으로 보호할 필요가 있다. labeler의 편집 가능 상태 검사는 있지만, 읽은 상태가 저장 시점에도 같은지를 보장하지 않는다.

프로젝트 조직 주석 클래스는 `open(..., "w")`로 저장한다. snapshot에 적용한 원자적 교체·충돌 정책을 클래스 편집에도 적용하면 동시 관리자 편집과 파일 쓰기 실패에 대응할 수 있다.

**AI 결과와 작업 관리**

- VS IHC는 모델 SHA-256을 확인한다. HE는 원본 서명, 후처리 버전, 일부 sTIL 버전, bbox 유무를 검사한 뒤 가중치를 읽기 전에 캐시를 반환한다. 검출·재분류·분할 모델을 교체해도 그 조건들이 같으면 이전 결과가 남을 수 있다. 실제 GPU 모델 교체 실험은 수행하지 않았다.
- PD-L1/IHC의 runtime metadata는 모델 파일명·크기·mtime와 아키텍처 등을 사용한다. 모든 파이프라인을 동일한 모델/전처리/후처리 식별 규약으로 정리할 필요가 있다.
- 작업 생성 시 사용자 ID를 작업 레코드에 넣지 않고, 조회·취소·결과 라우트에서도 소유자를 비교하지 않는다. 다른 사용자 소유라고 표시한 합성 작업도 labeler 요청으로 취소됐다. 작업 ID를 아는 경우의 재현이며 ID를 쉽게 추측할 수 있다는 주장은 아니다. 기관 내 전체 작업 관리가 의도라면 그 권한을 명시하고 취소 행위를 기록해야 한다.
- 결과는 JSON 직렬화 뒤 HTTP 전송이 끝나기 전에 메모리에서 해제한다. 같은 작업의 두 번째 요청은 410이다. 원래 디스크 캐시가 있어도 이 엔드포인트는 복구해서 반환하지 않는다. 재시도 가능한 결과 URL이나 캐시 복원 경로가 필요하다.

**성능과 확장성**

이전 SQL 개선은 유효하지만 모든 조회가 SQL 페이지 처리로 바뀐 것은 아니다. `application_store.py:304` 이후 정렬 분기는 후보를 읽고 Python에서 정렬·제한한다. 조건 있는 `count_documents()`도 후보 문서를 가져와 센다.

`cell_annotation.py:1574`의 패치 목록은 정렬 후 최대 200,000개를 한 응답으로 반환한다. 큰 프로젝트에서는 DB 처리뿐 아니라 JSON 전송·브라우저 메모리·렌더링 비용도 커질 수 있다. 자주 쓰는 정렬·필터를 전용 SQL로 옮기고 화면 요구 범위나 페이지 단위로 가져오는 개선이 적절하다. 실제 운영 지연 수치는 이번에 측정하지 않았다.

AI 작업 dict, 자동 작업 제어, 열린 슬라이드, 감사 체인 마지막 HMAC, 여러 잠금이 프로세스 내부에 있다. `start.sh`의 단일 Uvicorn 프로세스와는 맞지만 worker 수 증가만으로 수평 확장하기 어렵다. 확장이 필요하면 작업 소유·상태·예약을 공유 저장소로 옮기고, 감사 append 및 파일 snapshot의 다중 프로세스 동시성을 설계해야 한다.

기존 개선 보고서의 합성 DB 벤치마크는 저장소 계층 비교다. 통합 테스트는 이번에도 통과했지만 해당 개선 배율을 실브라우저 응답이나 GPU 속도로 해석하면 안 된다.

**프론트엔드·운영·문서**

`annotation.js` 7,870줄, `app.js` 6,189줄, `tile-viewer.js` 5,367줄이다. 단순히 줄 수 때문에 결함이라고 할 수는 없지만, 도형 조작·저장·다중 뷰·AI 표시의 변경 영향이 한곳에 집중돼 있다. 저장 상태, 도형 도구, Multi View 상태부터 경계를 나누는 편이 전면 재작성보다 검증하기 쉽다.

자동 프론트엔드 테스트는 12개로 면적과 주석 저장에 집중된다. 업로드→슬라이드 열기→AI 결과→편집→검수→내보내기, 브라우저 재접속·여러 탭·통신 중단은 별도 E2E 검증이 필요하다. 로컬 토큰 refresh 직렬화는 한 JS 모듈 인스턴스 범위이며, 서버에는 별도의 rotation grace 처리가 있으므로 여러 탭 동작은 양쪽을 함께 시험해야 한다.

`/api/health`는 고정 상태를 반환하며 DB 쿼리·디스크 쓰기 가능 상태·워커 생존을 확인하지 않는다. 서비스 가동 확인과 작업 준비 상태를 구분할 필요가 있다. 배포 문서는 PostgreSQL, 원본, AI 결과, DB 밖 annotation/export, 보안키의 동시 백업을 안내한다. 실제 복구 가능성은 복원 시험으로 확인해야 한다.

문서에는 현재 코드와 차이가 남아 있다. README는 RBAC 3단계로 설명하지만 실제 역할은 admin/doctor/labeler/viewer 4개다. VS IHC는 membrane/nucleus로 소개하지만 현재 `VS_MODEL_FILES`에는 membrane 하나가 등록돼 있다. annotation 전체가 DB에 저장되는 것으로 읽힐 수 있는 설명도 조직 JSON과 세포 DB 저장을 구분해야 한다. README의 Python 3.12 설명과 달리 이번 설치 환경의 테스트는 Python 3.10에서 실행됐다.

**권장 실행 순서와 완료 기준**

1. 업로드 ID·소유자·경로 검증 및 안전한 정리를 수정한다. 업로드 폴더 밖 쓰기·삭제가 어떤 실패 분기에서도 발생하지 않는 회귀 테스트를 추가한다.
2. MPP 유효성·출처를 API와 화면까지 전달한다. 보정 없는 원본에 확정 면적이 표시되지 않는 통합 테스트를 추가한다.
3. 세포 주석 revision과 상태 변경 트랜잭션을 도입한다. 오래된 저장은 충돌 응답을 내고 편집 내용을 보존해야 한다.
4. AI 모델 식별, 작업 권한, 결과 재시도 경로를 통일한다. 모델 교체·응답 손실·다른 사용자 취소를 각각 검증한다.
5. 큰 패치 목록의 SQL 정렬·페이지 처리와 실제 브라우저 부하를 측정한다. 이후 모듈 분리와 백업 복원·워커 준비 상태를 보완한다.

이번 작업은 재분석이며 애플리케이션 코드는 수정하지 않았다. 위 항목의 완료 여부는 이후 수정과 별도 검증으로 판단해야 한다.
