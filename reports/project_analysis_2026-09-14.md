**MeDIAuto Studio 전체 기술 분석 — 2026-09-14**

분석 기준: Git `ade2e9a`, 제품 버전 `2.0.2`.

이 프로젝트는 병원 내부에서 대용량 병리 슬라이드를 조회하고 AI 분석·조직 주석·세포 라벨링·검수·임상정보 관리를 수행하는 웹 플랫폼이다. 기능 범위와 WSI 처리 최적화는 상당히 발전해 있다. 다만 현재 구현을 기준으로는 권한 경계, 동시 편집 보호, 분석 결과 추적성과 운영 검증을 보완해야 한다. 구조적으로는 단일 기관·단일 애플리케이션 프로세스에 맞춰져 있으며, 여러 기관을 하나의 서비스에서 격리하는 SaaS 구조는 확인되지 않았다.

분석 범위는 저장소 구조, 주요 백엔드·프론트엔드 경로, 인증·저장·추론·배포 설정 및 기존 테스트다. 모든 코드 행에 대한 정밀 감사나 실제 GPU 추론·브라우저 전체 시나리오 검증은 아니다. 운영 DB와 실제 슬라이드에 쓰기 작업을 하지 않았으며, 권한 재현에는 임시 디렉터리·합성 데이터·모의 삭제 함수를 사용했다. 애플리케이션 코드는 변경하지 않았다.

**2. 아키텍처와 데이터 흐름**

브라우저의 Vanilla JS ES Modules가 동일 서버의 `/api`를 호출하고, FastAPI가 정적 화면과 API를 함께 제공한다. 타일은 Canvas 뷰어에서 필요 영역만 요청한다. 일반 API에는 Bearer JWT를, 이미지 URL에는 만료가 있는 HMAC 미디어 티켓을 사용한다.

업로드한 파일은 로컬 파일시스템에 저장한다. 슬라이드를 열면 포맷에 맞는 리더가 연결되고, 타일 생성·썸네일 생성·AI 작업은 별도 스레드 풀로 넘긴다. 사용자 AI 요청은 작업 ID를 받고 상태를 조회하며, 폴더 자동 AI는 뷰어·업로드 활동과 유휴 상태를 확인해 실행을 조절한다.

PostgreSQL은 SQLAlchemy/asyncpg로 연결한다. 사용자·세션·감사·임상정보는 전용 테이블을 사용하고, 프로젝트·슬라이드·패치 등은 `application_documents` JSONB 테이블에 컬렉션 형태로 저장한다. 기존 문서형 API를 유지하는 어댑터가 있어 이전 코드와의 호환성을 확보한 구조다.

| 저장 위치 | 데이터 | 운영상 의미 |
|---|---|---|
| PostgreSQL 전용 테이블 | 계정, 세션, 감사, 임상정보, 무결성 seal | 별도 마이그레이션과 DB 백업 필요 |
| PostgreSQL JSONB | 슬라이드, 프로젝트, AI 상태, 패치 주석·상태 등 | 문서 API 호환성은 좋지만 조회 비용과 제약 검토 필요 |
| `uploads/` | 원본 WSI | DB만 복원해서는 원본 복구 불가 |
| `tiles/` | 생성 타일 | 재생성 가능, 디스크·I/O 관리 필요 |
| `ai_results/` | 분석 결과, 가상 염색, 사용자 편집본 | 모델 버전과 함께 결과 재현성 관리 필요 |
| `annotations/` | 조직 주석 및 프로젝트 클래스 JSON | PostgreSQL 외 별도 영속 데이터 |
| 프로세스 메모리 | 실행 작업, 열린 슬라이드, 여러 lock·캐시 | 재시작·프로세스 증설 시 상태 공유 문제 |

따라서 “annotation은 모두 PostgreSQL에 저장된다”는 설명은 정확하지 않다. 조직 주석 JSON과 패치 주석의 저장 경로를 구분해서 백업해야 한다.

**3. 잘 구현된 부분**

- WSI 특성을 고려한 타일 피라미드, 원본 서명 확인, thread-local 슬라이드 핸들 및 캐시 정리가 있다.
- 웹·뷰어·타일·AI·업로드·패치 작업을 CPU/스레드 풀 수준에서 나누고 뷰어 활동에 양보하는 정책을 구현했다. 단일 장비에서 작업 간 경합을 줄이려는 설계가 분명하다.
- 가상 염색은 타일 단위로 결과를 기록하고, 완료된 대형 작업 결과는 다운로드 후 메모리에서 해제한다. 메모리 사용을 줄이는 의도가 코드에 반영되어 있다. 실제 최대 메모리는 측정하지 않았다.
- JWT 수명 분리, refresh rotation의 CAS 갱신, MFA 시드 암호화, 미디어 티켓, IP 제한, 감사 HMAC 등 보안 구성요소가 있다.
- 경로 검증에 `resolve()`/`relative_to()`를 사용하고 파일명 분리자·숨김 파일·NUL 등을 거부한다.
- Alembic 마이그레이션, 설치 사전 점검, PostgreSQL native/Docker 구성, 모델 manifest 및 배포 문서가 있다.
- 백엔드 라우터와 AI 파이프라인 분리가 진행되어 있어 기능별 개선을 시작할 경계가 존재한다.

권장 완료 기준은 모든 보호 라우터의 기본 인증, 역할별 서버 정책, 익명/viewer/labeler/doctor/admin별 API 회귀 테스트다. 삭제·이동·임상정보 수정·검수 종료 등 행위마다 역할 정책을 명시해야 한다. 조직 주석 저장에는 revision 또는 ETag 기반 충돌 검출과 원자적 파일 교체가 필요하다. 세포 주석의 전체 셀 목록 갱신도 동시 편집 충돌 정책을 함께 검토해야 한다.

**5. 데이터베이스·동시성·성능**

`application_store.py:285`의 cursor는 후보 문서를 읽은 뒤 Python에서 정렬·skip·limit·projection을 적용한다. `:363`의 `_find_documents()`는 후보 행을 `.all()`로 로딩한다. `_id`, 자연키, JSONB containment로 후보를 좁히는 최적화는 있으므로 모든 요청이 전수 조회인 것은 아니다. 그러나 넓은 필터, `$or`, 중첩 조건, 작은 limit이라도 후보 집합이 크면 DB 전송량과 Python 메모리 사용이 커진다.

`projects.py:56`은 프로젝트 목록 계산에 슬라이드 문서를 순회하고 디렉터리를 재귀 탐색한다. async 함수 내 동기 파일 탐색이므로 데이터가 늘면 이벤트 루프 지연 요인이 된다. 실제 지연 시간이나 동시 사용자 한계는 이번에 측정하지 않았다.

개선 순서는 자주 쓰는 조회에 SQL WHERE/ORDER BY/LIMIT와 필요한 열만 선택하도록 전용 repository를 추가하고, 대시보드 집계를 SQL이나 별도 집계 데이터로 옮기는 것이다. 패치·슬라이드 수를 늘린 합성 데이터로 응답 p95, DB 읽기량, RSS, 이벤트 루프 지연을 측정하면 우선순위를 정할 수 있다.

`_DICT_LOCKS`는 컬렉션 단위 프로세스 내부 lock이다. 기존 행 갱신에는 `FOR UPDATE`도 있으나 여러 프로세스가 없는 문서를 동시에 upsert하는 상황까지 내부 lock이 조정하지는 못한다. 고유 제약·충돌 처리와 관련 트랜잭션을 별도 검증해야 한다.

AI 작업 dict, 자동 작업 예약, 감사 체인의 마지막 HMAC, rate limiter와 슬라이드 핸들도 프로세스 메모리에 있다. Uvicorn worker 수만 늘리면 작업 조회 불일치, 자동 작업 중복, 감사 체인 분기 등이 발생할 수 있는 구조다. 현재 실행 스크립트는 단일 worker라 이 설계와 맞는다. 증설이 필요해질 때 작업 상태·예약·체인 append를 공유 저장소/트랜잭션 경계로 옮기는 것이 선행 조건이다.

Refresh rotation은 기존 토큰의 CAS 취소와 새 세션 insert가 각각 별도 트랜잭션이다(`auth_store.py:180`, `routers/auth.py:398`). 중간 장애나 동시 요청이 새 세션 생성 전 상태를 관찰하는 경우를 통합 테스트하고, 두 작업을 한 트랜잭션으로 묶는 개선을 검토할 수 있다.

**6. AI 결과 신뢰성과 작업 흐름**

검출·마커 분석·가상 염색 파이프라인과 scoring 함수가 분리되어 있다. 마커 파이프라인에는 runtime metadata 검사도 존재한다. 다만 이것만으로 모든 모델 교체·전처리 변경의 결과 무효화가 보장되는 것은 아니다.

가상 염색은 `cache_paths.py:39`에서 슬라이드 키와 target MPP로 경로를 정하고, `virtual_stain.py:377` 이후 원본 서명이 일치하면 캐시를 반환한다. 이 캐시 적중 구간에는 모델 가중치 버전/해시 검사가 없다. 원본과 MPP가 같고 가중치만 교체되면 이전 결과를 재사용할 수 있다. 현재 실행 가능한 stain type은 하나이므로 복수 stain 간 충돌을 현재 재현된 결함으로 보지는 않았다. 향후 종류 추가 시 키에 stain type도 포함해야 한다.

작업 결과 다운로드는 `routers/ai.py:294`에서 직렬화 직후 메모리를 해제한다. 응답 전송이 실패해도 후속 조회는 410이 될 수 있다. 디스크 캐시에서 동일 결과를 다시 제공하거나 다운로드 재시도를 처리할 경로가 필요하다.

작업 ID의 소유자·프로젝트 접근권한도 향후 분리 대상이다. 현재 AI 라우터는 역할 인증은 있지만 작업 생성·취소·결과 조회가 사용자별 소유권을 기준으로 제한되지는 않는다. 기관 내 공유 업무 정책이라면 이를 명시하고, 사용자별 격리가 필요하면 작업 소유권 검사를 추가해야 한다.

분석 결과에는 원본 식별자·모델 해시·전처리 설정·threshold·MPP·실행 버전·생성 시각을 일관되게 남기는 것이 좋다. 모델 성능, 임상적 유효성, 규제 적합성은 이번 코드 분석으로 판정하지 않았다.

**7. 프론트엔드와 유지보수성**

빌드 없이 정적 자원을 배포할 수 있어 단순한 설치에 유리하다. API 클라이언트는 토큰 갱신 중복을 같은 JS 컨텍스트 안에서 직렬화하고 미디어 티켓을 미리 준비한다. 뷰어는 전용 Canvas 타일 처리와 annotation layer를 갖춘다.

반면 큰 파일에 상태·UI·통신·렌더링 처리가 집중되어 있다. `annotation.js` 7,858줄, `app.js` 6,182줄, `tile-viewer.js` 5,323줄, `visualization.js` 3,028줄이다. 프레임워크 교체보다 저장 상태, 도형 편집, AI 작업 상태, 화면별 이벤트 처리를 기존 모듈 경계 안에서 분리하는 편이 변경 위험을 줄인다.

Access/Refresh token은 `api.js:9`부터 localStorage에 저장된다. 실제 XSS를 재현한 것은 아니지만 DOM 삽입 경로와 보안 헤더를 함께 검토해야 하는 구조다. 여러 렌더링 지점에 escape helper를 사용하는 방어도 확인된다. 토큰 정책 변경 시에는 API 호출 방식과 CSRF 정책까지 함께 설계해야 한다.

여러 Python 주석·오류 문자열이 `text` 또는 `????`로 남아 있다. 단순 서식 문제가 아니라 장애 원인 파악과 사용자 오류 안내 품질을 떨어뜨린다. 사용자에게 반환되는 메시지부터 복구하고, 반복 로직을 분리할 때 내부 문서도 정리할 필요가 있다.

**8. 설치·배포·운영**

Conda 기반 실행, PostgreSQL 영속화, 모델 공급 및 사전 점검은 준비되어 있다. 다만 requirements는 일부만 고정 버전이고 다수 라이브러리가 범위 지정이며, Git에 설치 전체를 재현하는 lockfile은 확인되지 않았다. 이번 테스트에 사용한 기존 `medicus-saas` 환경은 Python 3.10이고 README의 Python 3.12와 차이가 있다. 테스트 통과가 새 설치의 재현성을 증명하지는 않는다.

`start.sh:27`의 기본 포트는 8092지만 README 구조 설명에는 8091이 남아 있다. 출시 채널이 production이라는 메타데이터만으로 운영 검증 완료를 의미하지도 않는다. 역할 수·가상 염색 지원 종류·주석 저장 위치·실행 환경의 문서 차이를 함께 정리해야 한다.

`main.py`의 `/api/health`는 고정 상태를 반환하므로 실행 중 DB·디스크·작업 상태를 판단하는 readiness 점검은 아니다. TLS·보안 헤더·프로세스 감독은 배포 문서에 있으나 실제 운영 프록시 설정은 이번에 점검하지 않았다. 문서상 요구와 적용 여부를 분리해 확인해야 한다.

`geo.py:27`은 공인 IP 위치 조회에 외부 HTTP API를 사용한다. 온프레미스라고 해서 외부 통신이 없는 제품은 아니다. 외부 전송이 필요한 운영인지 정하고 비활성화 옵션 또는 로컬 위치 데이터 사용을 검토해야 한다. 이번 분석 과정에서는 이 API를 호출하지 않았다.

`.secrets.json` 로딩 실패 시 `config.py:22`가 빈 값으로 처리해 새 키를 생성·기록할 수 있다. 기존 키가 손상된 운영 환경에서 자동 재생성은 암호화 데이터·로그인·감사 검증에 영향을 줄 수 있으므로, 최초 설치와 기존 키 읽기 실패를 구분해야 한다. 실제 키 값은 보고서에 포함하지 않았다.

백업은 DB, 원본, AI 결과, 조직 주석·클래스, 필요한 패치 산출물, 모델, 영구 비밀키를 함께 고려해야 한다. 저장소 작업 공간에는 약 100.8 GB의 `project.tar`도 있다. Git 추적에서는 제외되어 있지만 운영 데이터·배포 코드·백업 파일의 수명주기를 분리하면 용량 관리가 쉬워진다.

권한 재현은 해당 router를 독립 FastAPI 앱에 마운트해 수행했고, 실제 `main.py`에 추가 인증 의존성이 없는 것을 정적으로 확인했다. 운영 서버 침투 시험은 수행하지 않았다. 삭제 재현은 실제 파일 삭제 함수를 대체했으므로 운영 데이터 손실은 발생하지 않았다.

기존 테스트는 저장소 helper, 설치 도구, 포맷 어댑터, rate limit, scoring 일부 등을 검증한다. 전체 API 권한 행렬, 실제 PostgreSQL 동시 트랜잭션, 브라우저 저장·검수 흐름, GPU 추론 정확도·성능, 백업 복구는 이번 통과 결과의 범위 밖이다. Git 추적 CI 설정이나 프론트엔드 E2E 테스트 구성은 확인되지 않았다.

**10. 권장 작업 순서**

1. 인증 누락과 viewer 변경 권한을 먼저 수정하고 API 권한 회귀 테스트를 추가한다. DB 미연결 허용 분기와 미디어 계정 상태 검사도 함께 통일한다.
2. 조직·세포 주석의 저장 revision/충돌 처리와 원자적 쓰기를 적용하고, 감사 before/after를 포함하는 버전 있는 서명 형식을 도입한다. 기존 감사 기록을 무작정 재서명하지 않는다.
3. VS 캐시의 모델 버전 무효화, 분석 결과 재다운로드, 작업 소유권 정책을 정리한다.
4. 실제 규모의 합성 데이터로 대시보드·패치 조회를 측정하고 Python 정렬/페이지 처리를 SQL로 이동한다.
5. 설치 환경을 고정하고 CI에 기존 테스트·권한 테스트·구문 검사를 연결한다. 브라우저의 로그인→업로드→주석 저장→새로고침→검수 시나리오를 검증한다.
6. 운영 readiness, 작업 지표, 복구 훈련과 문서 일치 여부를 확인한다. 여러 기관·여러 프로세스 운영이 요구될 때 테넌트 권한과 영속 작업 큐를 설계한다.

현재 투자 우선순위는 새 화면이나 AI 종류 확대보다 기존 기능의 접근권한과 데이터 보존을 확실하게 만드는 데 있다. 이 기반을 갖춘 뒤 조회 병목을 줄이면 이미 구현된 WSI·AI·주석 기능을 더 안정적으로 활용할 수 있다.
